
# Introduction

This is a imagination Saas comapany Omena. I want to design a copilot knowledge agent (called Jarvis Knowledge Asisstant)

There are two type of users in the app:
- Subscriber (customer) who want to send questions about the product
    - Customer can send message to ask about certain details of the product
- Customer support (employees from Omena)
    - Employee can upload documents to create knowledge base

The important feature for employee is the support inbox. It's like a mailbox contains context. I helps employee draf a response based on the knowledge base and provide evidence. Employee can edit draft, re-geneate answers or approve the message generated by LLM.

# LLM usage
My starting choice is the paid Gemini Developer API, using a low-cost Flash-family model for generation and an embedding model for retrieval. Google offers an embedding API, so you can initially use one provider. ai.google.dev

# Cost control

| Control | Suggested prototype starting point |
|---|---|
| Context limit | Around 6,000 input tokens per draft |
| Answer length | Around 800 output tokens |
| Calls | One generation call per draft initially |
| Retries | Maximum two retries for transient failures |
| User quota | For example, 30 drafts per day |
| Upload quota | For example, 10 MB and 100 pages per document |
| Spending limit | Application-enforced daily and monthly budgets |
| Reindexing | Embed only new or changed content |

# Security
- Employee must login into the system. To keep it simple everybody has the same roles
- Document must have limit size and file types
- Send only necessary data to providers.
- Keep API keys on the backend. Never put them in browser code; Google explicitly recommends server-side calls for key protection. ai.google.dev
- Authenticate generation and upload endpoints. Apply per-user quotas and concurrency limits.
- Filter access before retrieval. Select only chunks the authenticated user may access; authorization must not depend on the prompt.
- Keep files and the database private. Use short-lived authorized download links.
- Treat uploaded content as untrusted. Give the model no email, database-write, or arbitrary - URL-fetching tools in this version.
- Process uploads in an isolated worker with file-type validation, size limits, and processing timeouts.
- Render Markdown safely. Disable raw HTML or sanitize it.
- Avoid logging document text and customer details. Log request IDs, model, token counts, timings, and errors.
- Send only necessary data to providers. Remember that hosted embedding calls also send document text outside your application.
- Delete derived data too: original files, extracted text, chunks, embeddings, and relevant caches.

# Design
Two separate piplines

| Upload/indexing pipeline | Question/answer pipeline |
|---|---|
| Validate PDF or Markdown upload | Authenticate user |
| Save original file in private storage | Embed the question |
| Extract text, preserving headings and PDF page numbers | Retrieve relevant, authorized chunks from active versions |
| Split text into chunks | Assemble question, customer context, and retrieved text |
| Generate embeddings for chunks | Call the generation model |
| Store text, embeddings, and metadata | Validate response and citation IDs |
| Mark document version ready | Save draft and return it to the UI |
